# Решения и допущения

Это тестовое задание, поэтому я не стал ждать ответов на уточняющие вопросы и принял решения сам.
Каждое записано в формате «вопрос → решение → почему». В реальном проекте я бы согласовал их с руководителем.

## Безопасность

- **Где хранится роль пользователя?** → В таблице `profiles`, пользователь не может её изменить. → Метаданные пользователя в Supabase
  (`user_metadata`) пользователь меняет сам, и это позволило бы исполнителю назначить себя постановщиком.
- **Как запрещены переходы статусов?** → Статус меняется только через одну функцию в базе, которая проверяет роль, исполнителя,
  допустимость перехода и комментарий, а также сама пишет историю. Напрямую поменять статус в таблице нельзя.
- **Новые таблицы не открываются в API автоматически.** → Каждой таблице права выдаются явно в миграции. → Так ничего не окажется
  доступным случайно.

## Неоднозначности ТЗ

> Черновик: окончательно фиксируется на этапе 2.

- **Что происходит с историей при удалении задачи?** → _Предлагаю:_ задача не удаляется физически, а архивируется: она исчезает из
  интерфейса, а история остаётся. → Иначе постановщик мог бы стереть историю, просто удалив задачу, и требование «историю нельзя удалить» теряло бы смысл.
- **Можно ли удалить объект, в котором есть задачи?** → _Предлагаю:_ нельзя, сначала нужно разобраться с задачами. → Защита от случайной потери данных.
- **Можно ли переназначить исполнителя?** → _Предлагаю:_ да, постановщик может переназначить в любом статусе, кроме «Принята».
  Смена исполнителя в историю статусов не пишется (ТЗ просит историю именно статусов).
- **Можно ли редактировать принятую задачу?** → _Предлагаю:_ нет, после «Принята» задача только для чтения.
- **Кто может быть исполнителем?** → Только пользователь с ролью «исполнитель». Постановщик не назначает задачи сам себе.
- **Видит ли исполнитель в карточке объекта чужие задачи?** → Нет, только свои. Объект он видит, если у него там есть хотя бы одна задача.
- **Видят ли пользователи имена друг друга?** → Да, имена и роли видны всем вошедшим: это нужно, чтобы показать автора, исполнителя
  и того, кто менял статус в истории. Email других пользователей не показываются.

## Инфраструктура

- Supabase cloud, бесплатный тариф, регион eu-west-1 (Ирландия; планировался Frankfurt, на работу не влияет).
  Бесплатный проект засыпает после 7 дней без активности: если ссылка не открывается, проект нужно «разбудить» в панели Supabase.
- Фронтенд на Vercel. Все адреса ведут на `index.html` (`vercel.json`), маршрутами управляет React Router.
- **Открытая регистрация выключена** (`enable_signup = false` в `supabase/config.toml`). → Пользователей создаёт скрипт
  с серверным ключом. → В ТЗ три фиксированных пользователя, а открытая регистрация позволила бы любому завести аккаунт.
- **Ключи.** Во фронтенд попадают только адрес проекта и публичный ключ (`sb_publishable_…`): он ничего не разрешает сам по себе,
  права проверяет база. Секретный ключ лежит только в `.env` на моей машине и используется скриптами наполнения и проверки.
