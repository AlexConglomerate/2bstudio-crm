# Решения и допущения

Это тестовое задание, поэтому я не стал ждать ответов на уточняющие вопросы и принял решения сам.
Каждое записано в формате «вопрос → решение → почему». В реальном проекте я бы согласовал их с руководителем.

## Безопасность

- **Где хранится роль пользователя?** → В таблице `profiles`, пользователь не может её изменить. → Метаданные пользователя в Supabase
  (`user_metadata`) пользователь меняет сам, и это позволило бы исполнителю назначить себя постановщиком.
- **Как запрещены переходы статусов?** → Статус меняется только через одну функцию в базе, которая проверяет роль, исполнителя,
  допустимость перехода и комментарий, а также сама пишет историю. Напрямую поменять статус в таблице нельзя.
- **Новые таблицы не открываются в API автоматически.** → Каждой таблице права выдаются явно в миграции. → Так ничего не окажется
  доступным случайно.
- **Права выдаются не на всю таблицу, а на отдельные колонки.** → Постановщик может менять у задачи только название, описание,
  объект и исполнителя. Статус, автора и дату создания через API не изменить никому: автора и дату ставит сама база,
  статус меняет только функция смены статуса.
- **Что видит исполнитель, если попытается сменить статус чужой задачи?** → Ответ «Задача не найдена» — тот же, что для
  несуществующей. → Так он не может даже проверить, существует ли чужая задача.
- **Проверка защиты автоматизирована.** → Скрипт `scripts/security-check.ts` заходит под каждым пользователем, как браузер,
  и пробует больше 40 запрещённых действий в обход интерфейса; затем проверяет, что данные в базе не изменились,
  и что разрешённые действия по-прежнему работают.

## Неоднозначности ТЗ

- **Можно ли удалить задачу и что тогда с историей?** → Удалить можно только задачу в статусе «Новая»: её ещё не брали в работу,
  истории у неё нет. Задачу, по которой уже была работа, удалить нельзя. → Иначе постановщик мог бы стереть историю, просто
  удалив задачу, и требование «историю нельзя удалить» теряло бы смысл. Рассматривал «архив» (задача скрыта, история осталась),
  но это лишняя колонка и отдельная функция ради сценария, которого в ТЗ нет; правило «удаляется только новая» проще объяснить и проверить.
- **Можно ли удалить объект, в котором есть задачи?** → Нельзя, сначала нужно удалить задачи. Объект, где задачи уже были в работе,
  удалить нельзя совсем. → Защита от случайной потери данных; держит сама база (внешний ключ), а не интерфейс.
- **Обязателен ли исполнитель при создании задачи?** → Да, задача всегда создаётся сразу с исполнителем. → Без исполнителя её
  некому взять в работу, а статус «Новая» в ТЗ означает «ждёт исполнителя».
- **Можно ли переназначить исполнителя?** → Да, постановщик может переназначить в любом статусе, кроме «Принята».
  Смена исполнителя в историю статусов не пишется (ТЗ просит историю именно статусов).
- **Можно ли редактировать принятую задачу?** → Нет, «Принята» — конечный статус: из него нет переходов, и задачу больше
  не редактируют.
- **Кто может быть исполнителем?** → Только пользователь с ролью «исполнитель». Постановщик не назначает задачи сам себе
  и не может нажимать кнопки исполнителя за него («взять в работу», «на проверку»).
- **Какой постановщик принимает задачу?** → Любой. ТЗ говорит, что постановщиков может быть несколько и что постановщик
  «видит всё», поэтому принять или вернуть задачу может не только её автор.
- **Пишется ли в историю создание задачи?** → Нет, в истории только смены статуса. Кто и когда создал задачу, видно из полей
  «автор» и «дата создания» — их нельзя подделать.
- **Комментарий при других переходах?** → Можно оставить при любом переходе, обязателен — только при возврате на доработку.
  Комментарий из одних пробелов считается пустым.
- **Видит ли исполнитель в карточке объекта чужие задачи?** → Нет, только свои. Объект он видит, если у него там есть хотя бы одна задача.
- **Видят ли пользователи имена друг друга?** → Да, имена и роли видны всем вошедшим: это нужно, чтобы показать автора, исполнителя
  и того, кто менял статус в истории. Email других пользователей не показываются.

## Интерфейс

- **Кнопки в интерфейсе — подсказка, а не защита.** → Список «кто какой переход делает» продублирован в коде интерфейса
  (`src/lib/status.ts`), чтобы показывать только доступные кнопки. Если они когда-нибудь разойдутся с базой, база всё равно
  не пропустит лишнее.
- **Комментарий при возврате на доработку проверяет база, а не форма.** → Интерфейс отправляет запрос как есть и показывает
  ответ базы «комментарий обязателен». → Правило живёт в одном месте, и это видно прямо в интерфейсе.
- **«Мои задачи» — только в меню исполнителя.** → Постановщику задачи не назначаются, ему этот экран не нужен.
  Главная страница у всех — список объектов; исполнитель видит в нём только объекты со своими задачами.
- **Чужая задача или объект по прямой ссылке** → «не найдено», как и для несуществующей записи: база просто не отдаёт строку.
- **Удаление** — с подтверждением. Кнопка «Удалить» у задачи видна только в статусе «Новая», «Редактировать» — во всех
  статусах, кроме «Принята». Объект с задачами не удаляется: показывается понятная ошибка.

## Инфраструктура

- Supabase cloud, бесплатный тариф, регион eu-west-1 (Ирландия; планировался Frankfurt, на работу не влияет).
  Бесплатный проект засыпает после 7 дней без активности: если ссылка не открывается, проект нужно «разбудить» в панели Supabase.
- Фронтенд на Vercel. Все адреса ведут на `index.html` (`vercel.json`), маршрутами управляет React Router.
- **Открытая регистрация выключена** (`enable_signup = false` в `supabase/config.toml`). → Пользователей создаёт скрипт
  с серверным ключом. → В ТЗ три фиксированных пользователя, а открытая регистрация позволила бы любому завести аккаунт.
- **Пароль демо-пользователей не лежит в репозитории.** → Он задаётся в `.env` (`SEED_PASSWORD`) и передаётся проверяющим отдельно.
  → Репозиторий открытый: пароль в коде позволил бы любому зайти и поменять демо-данные.
- **Ключи.** Во фронтенд попадают только адрес проекта и публичный ключ (`sb_publishable_…`): он ничего не разрешает сам по себе,
  права проверяет база. Секретный ключ лежит только в `.env` на моей машине и используется скриптами наполнения и проверки.

## Не успел / сознательно не делал

ТЗ рассчитано на 2–3 часа, поэтому всё, что ниже, отложено. Ничего из этого не ослабляет защиту.

- **Автотестов интерфейса в репозитории нет.** Сценарии за всех трёх пользователей (около 50 проверок: создание,
  редактирование, удаление, весь цикл статусов, чужое по прямой ссылке) я прогнал в браузере скриптом на Playwright —
  локально и на развёрнутой версии, — но в проект его не оформлял. Защиту базы проверяет `pnpm security-check`, он в репозитории.
- **Нет обновления в реальном времени.** Если постановщик принял задачу, исполнитель увидит это, когда вернётся на вкладку
  или перейдёт на другую страницу, а не мгновенно. Для небольшой команды достаточно; при необходимости — подписка Supabase Realtime.
- **Нет поиска, фильтров по статусу и постраничного вывода.** На демо-данных не нужны, на сотнях задач понадобятся.
- **Нет управления пользователями в интерфейсе.** Добавить пользователя, сменить роль или сбросить пароль можно только
  скриптом или в панели Supabase. Это осознанно безопасный вариант: роль не меняется ни через какой пользовательский запрос.
- **В журнал пишутся только смены статуса.** Кто переименовал задачу или сменил исполнителя, не сохраняется — ТЗ просит
  историю статусов. Если понадобится, это ещё одна таблица только для чтения, которую заполняет триггер.
- **Нет сроков, приоритетов и фото к задачам.** В ТЗ их нет, но для стройки это первое, что попросят.
- **Под телефон отдельно не доводил.** На ширине телефона (390 px) экраны читаются и не уезжают вбок, но меню и таблицы
  можно сделать удобнее.
