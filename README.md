# Объекты и задачи — мини-CRM для строительной компании

Тестовое задание для 2B Studio. Постановщик ставит задачи по объектам (стройкам), исполнитель берёт их в работу
и отдаёт на проверку, постановщик принимает или возвращает на доработку. Каждая смена статуса попадает в историю.

- Приложение: https://2bstudio-crm.vercel.app
- Стек: React + TypeScript + Vite, Tailwind + shadcn/ui, TanStack Query, React Hook Form + Zod; Supabase (Postgres + RLS + SQL-функции).
  Своего сервера нет: все права проверяет база.

## Запуск локально (против уже настроенной облачной базы)

Нужны Node 22+ и pnpm.

```bash
pnpm install
cp .env.example .env   # заполнить VITE_SUPABASE_URL и VITE_SUPABASE_ANON_KEY
pnpm dev               # http://localhost:5173
```

## Развернуть свою копию с нуля

1. Создать проект в [Supabase](https://supabase.com) (бесплатный тариф подходит).
2. Заполнить `.env` по образцу `.env.example`: ref проекта, пароль БД, URL, publishable key, secret key, пароль демо-пользователей.
3. Применить миграции и настройки входа, наполнить базу:

   ```bash
   supabase login
   supabase link --project-ref <ref>
   supabase db push        # таблицы, права, RLS, функция смены статуса — supabase/migrations/
   supabase config push    # выключает открытую регистрацию — supabase/config.toml
   pnpm seed               # 3 пользователя, 3 объекта, 7 задач (статусы меняются через ту же функцию, что в приложении)
   pnpm security-check     # попытки обойти права напрямую через API — все должны упасть
   ```

   В `supabase/config.toml` адрес сайта (`site_url`) указывает на мой деплой — для своей копии его нужно поменять.

4. Фронтенд на Vercel: импортировать репозиторий, задать `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`.
   Все адреса ведут на `index.html` (`vercel.json`), маршрутами управляет React Router.

Секретный ключ (`SUPABASE_SERVICE_ROLE_KEY`) нужен только скриптам `seed` и `security-check` на машине автора.
Во фронтенд и в Vercel он не попадает.

## Структура

```
supabase/
  migrations/
    …_schema.sql        таблицы, enum статусов и ролей, связи, индексы
    …_rls.sql           права на таблицы и колонки (grants) + политики строк (RLS), is_manager()
    …_task_status.sql   change_task_status() — единственный способ сменить статус; проверка роли исполнителя
  config.toml           настройки входа: регистрация выключена
scripts/
  seed.ts               демо-данные
  security-check.ts     атаки в обход интерфейса под каждым пользователем и без входа
src/
  api/                  все запросы к базе (TanStack Query): objects, tasks, profiles
  lib/status.ts         названия статусов и таблица переходов — только чтобы показать нужные кнопки
  lib/errors.ts         ошибки базы → понятный текст на русском
  pages/                экраны: вход, объекты, карточка объекта, карточка задачи, формы, «Мои задачи»
docs/
  for-manager.md        объяснение для руководителя без терминов
  decisions.md          решения и допущения, что не успел
```

## Как устроена защита (коротко)

- **Роль** хранится в таблице `profiles`, а не в метаданных пользователя: метаданные пользователь может менять сам.
- **Права на двух уровнях.** `grant` решает, какие действия и с какими колонками разрешены вошедшему пользователю;
  RLS-политика решает, с какими строками. Исполнитель видит только свои задачи и объекты, где они есть.
  Не вошедшему (`anon`) не выдано ничего.
- **Статус** нельзя поменять обычным UPDATE (на колонку `status` нет права). Только функция `change_task_status`:
  она проверяет роль, что исполнитель назначен на эту задачу, что переход разрешён и что при возврате есть комментарий,
  и сама пишет историю.
- **История** доступна только на чтение: прав на запись, изменение и удаление ни у кого из пользователей нет.
- **Исполнителем** можно назначить только пользователя с ролью «исполнитель» — проверяет триггер в базе.
- **Регистрация** выключена, пользователей создаёт скрипт с секретным ключом.

Интерфейс только прячет недоступные кнопки. Если отправить запрос в обход него, база всё равно откажет —
это и проверяет `pnpm security-check`.
